# 1 Provisional title

Spec-Driven for Agentic Software Development: A Characterisation and Comparison of Existing Approaches

# 2 Introduction and problem

AI coding agents now carry out complete development tasks.
They analyse repositories, plan changes, modify several files and run tests.
Spec-Driven Development (SDD) proposes that the specification should be the central artefact of this work, giving the agent persistent and structured context.
In little more than a year, several approaches have emerged, such as GitHub Spec Kit [@githubSpecKit2025], OpenSpec, Kiro and the BMAD Method.
They differ in the artefacts they require, the phases of the process and the points of human review [@macedoPromptProcessProcess2026].

The choice matters because more structure is not free.
Context files generated by a model raised the cost of coding agents by about 20%, with no significant gain in success [@gloaguenEvaluatingAGENTSmdAre2026].
An SDD approach can likewise add cost without adding quality.
The available comparisons are almost all grey literature.
Macedo [-@macedoPromptProcessProcess2026] compares six frameworks from their documentation and measures neither cost nor quality.
Panda [-@pandaCitationDisciplineSpecDriven2026] runs three approaches, but compares output determinism and hallucination detection, not cost.
The problem, as stated in the approved formalisation, is:

> The lack of a comparison of the results of the existing SDD standards when applied to the same project, supported by an up-to-date common characterisation of them.

The SDD method, its flow of phases, is the object of comparison.
The agent and the model are recorded factors, not evaluated in themselves, and no new SDD approach is created.

The stakeholders were analysed with a power × interest matrix.
The student and the supervisor (sponsor) are managed closely.
The course head, the examination panel and ISEP/P.PORTO, through its code of ethics, are kept satisfied.
The agent supplier, the SDD approach creators and the teams adopting SDD are monitored.
These teams use the results: a poor choice costs them agent usage, rework and dependence on one workflow.

# 3 Research questions and objectives

The main research question comes from the approved formalisation:

> Which Spec-Driven Development approaches exist for development with agents, how do they differ, and how do they affect the total cost and the quality of development when applied to the same project?

The main objective is "to identify and characterise the existing Spec-Driven Development standards for development with agents, and to compare their effect on the total cost and the quality of development when applied to the same project".
The specific objectives are:

- **O1.** Identify the existing SDD standards and characterise them in a common comparative framework: what each one prescribes and how it can be used.
- **O2.** Design a reproducible evaluation protocol, with a reference project and cost and quality metrics defined in advance.
- **O3.** Apply each approach to the same example project, together with a baseline without a structured specification.
- **O4.** Compare the results of the approaches, with each other and with the baseline.
- **O5.** Produce a decision guide on which approach to use in which situation.

The contributions are the comparative framework (O1) and an open, reproducible evaluation protocol with its reference project (O2).
They also include comparable cost and quality data (O3, O4) and the decision guide (O5).

The blocks are SDD (A1: "spec-driven", "spec kit", OpenSpec), context mechanisms (A2: "AGENTS.md", "context file*") and coding agents (B: "coding agent*", "agentic coding").
They also cover comparative evaluation (C: benchmark*, "controlled experiment*") and metrics (D: "token usage", "code quality", "human effort").
IEEE Xplore, Web of Science, the ACM Guide to Computing Literature and arXiv were searched, from 2023 to 18 Nov 2026.
arXiv is included because SDD for agents appeared in 2025 and peer-reviewed work is scarce; Scopus was dropped, as ISEP has no licence.

**Inclusion and exclusion criteria.**
Included are English studies from 2023 on, with full text, on SDD with coding agents, related context mechanisms, or the evaluation of coding agents.
Excluded are single-function code generation, formal specification without agents, editorials, and earlier versions of an included study.
For agent evaluations, only feature- or project-level development, or a contribution to the evaluation method, is kept.

**Selection.**
The search identified 2131 records (arXiv 1605, IEEE Xplore 167, Web of Science 133, ACM 226).
After removing 273 duplicates, 1858 records were screened on title and abstract, and 328 went to full text.
Of these, 246 were included, each quality-assessed with a 13-question checklist and extracted with a piloted form.
Tool documentation and repositories are analysed in a separate track, rated with the 5W source evaluation matrix.

# 5 Proposed method

The research process follows @oatesResearchingInformationSystems2006 and combines two strategies.
Design and creation produces the evaluation protocol, the reference project, the metrics and, later, the decision guide.
An experiment applies each selected approach, and a baseline without a structured specification, to the same reference project.
The baseline is adapted from @gloaguenEvaluatingAGENTSmdAre2026, who compare each condition with a no-context baseline on the same tasks.
Data come from documents, observation of the agent runs, and the logs and metrics of each run.
Metrics are compared quantitatively, reporting spread and using non-parametric tests [@wohlinExperimentationSoftwareEngineering2012]; the rest is synthesised qualitatively.

The design fits the available resources.
The reference project is new and synthetic, with 8 to 10 features, and is checked by external acceptance tests.
Metrics, tests and prompts are fixed before any run, and each condition is repeated.
Runs use the author's Claude Pro plan and local models, in isolated copies outside the repository.
The protocol is evaluated by its repeatability, and the decision guide on tasks not used to build it.

# 7 Ethical and professional considerations

The work follows the ACM Code of Ethics [@associationforcomputingmachineryACMCodeEthics2018] and the ALLEA research integrity principles [@allea-alleuropeanacademiesEuropeanCodeConduct2023].
Each principle of ACM sections 1 and 2 is tied to a practice.
Metrics and tests are fixed before any run, all results are reported, and all approaches run under the same conditions.

There are no human participants, personal data or confidential information; the reference project is original.
Article 10 of the P.PORTO code requires ethics review "as required by law" for research with autonomous AI systems [@institutopolitecnicodoportoRegulamentoCodigoBoas2020].
The agents run in isolation on synthetic material, so no legal requirement applies; confirmation was asked of the supervisor.
The terms of use of each tool are checked for research use and code ownership.
Research data are published openly under the FAIR principles [@wilkinsonFAIRGuidingPrinciples2016].
One conflict is declared: Claude is both an agent under study and the assistant for this work, and every AI use is logged.

Professional competence is ensured by a development plan.
A self-assessment, checked by a colleague, chose three key competencies: critical thinking, time management and written communication.
Each has two actions with a metric and a target, reviewed weekly.
